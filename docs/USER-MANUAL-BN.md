## ১. SlotFlow কী এবং কোন সমস্যা সমাধান করে

ধরুন একটি সেলুন, একটি ফিজিও ক্লিনিক, বা একজন গৃহশিক্ষক। তিনটি চেয়ার, কোনো IT টিম নেই। এমন ব্যবসা তিনভাবে টাকা হারায়:

| যা ঘটে | যা খরচ হয় |
|---|---|
| একই সময়ে দুইজন কাস্টমার বুক হয়ে যায় | একজনকে দরজা থেকে ফিরিয়ে দিতে হয় |
| কাস্টমার আসেই না (no-show) | সময়টা নষ্ট — এবং আগে থেকে কেউ বুঝতেও পারেনি |
| ক্যালেন্ডার উইজেট জটিল লাগায় কাস্টমার হাল ছেড়ে দেন | বুকিংটাই আর হয় না |

SlotFlow এই তিনটির উত্তর:

1. **ডাবল বুকিং ডেটাবেজ লেভেলে বন্ধ** — অ্যাপ্লিকেশন কোডে "চেক করে তারপর লিখি" নয়।
2. **নো-শো রিস্ক স্কোর** — প্রতিটি বুকিং কতটা ঝুঁকিপূর্ণ, এবং কেন, তার পূর্ণ ব্যাখ্যা।
3. **সাধারণ ভাষায় বুকিং** — "আগামী মঙ্গলবার বিকেলে একটা হেয়ারকাট" লিখলেই আসল খালি স্লট চলে আসে।

**গুরুত্বপূর্ণ:** এটি একটি পোর্টফোলিও প্রজেক্ট, বিক্রয়যোগ্য প্রোডাক্ট নয়। ভেতরের স্টুডিও, কাস্টমার, বুকিং — সব কল্পিত ডেটা। কিন্তু কোনো ফিচার নকল নয়: কনকারেন্সি গার্ড আসল প্রসেস fork করে টেস্ট করা হয়, অ্যাভেইলেবিলিটি ইঞ্জিন daylight saving সামলায়, এবং AI ফিচার বন্ধ থাকলে অ্যাপ ভাঙে না — একটি নির্দিষ্ট (deterministic) বিকল্পে নেমে আসে।

## ২. ব্যবহারকারীর ধরন ও তাদের ক্ষমতা

তিন ধরনের ব্যবহারকারী আছে, এবং অনুমতি **প্রতি রেকর্ড ধরে** পলিসি দিয়ে যাচাই হয় — শুধু রুট লেভেলে নয়।

| ভূমিকা | কী দেখেন | কী করতে পারেন | কী পারেন না |
|---|---|---|---|
| **Owner** (মালিক) | সম্পূর্ণ অ্যাডমিন প্যানেল | সার্ভিস, টিম, সময়সূচি, ছুটি, সব বুকিং, AI প্রোভাইডার ও বাজেট | — |
| **Staff** (কর্মী) | শুধু নিজের ডায়েরি | নিজের বুকিংয়ের স্ট্যাটাস বদলানো, সব AI ফিচার ব্যবহার, AI ব্যবহারের পেজ দেখা | API key সংক্রান্ত কিছুই দেখতে বা বদলাতে পারেন না |
| **Customer** (কাস্টমার) | নিজের বুকিং ইতিহাস | বুকিং করা, নির্দিষ্ট সময়সীমার মধ্যে নিজেই বাতিল করা | অন্য কারো তথ্য দেখা |
| **অতিথি** (লগইন ছাড়া) | ল্যান্ডিং পেজ, সার্ভিস, বুকিং ফর্ম | পূর্ণ বুকিং করা — অ্যাকাউন্ট ছাড়াই | — |

> **কেন বুকিং পাবলিক?** কাস্টমারকে আগে অ্যাকাউন্ট খুলতে বাধ্য করা হলো বুকিং হারানোর সবচেয়ে সহজ উপায়। তাই `POST /api/v1/bookings` টোকেন ছাড়াই কাজ করে।

**API key নিয়ে বিশেষ নিয়ম:** AI প্রোভাইডারের ক্রেডেনশিয়াল শুধু Owner দেখতে ও বদলাতে পারেন — ঠিক যেমন পেমেন্ট মেথড। Staff প্রতিটি AI ফিচার ব্যবহার করেন, কিন্তু কোন key দিয়ে বিল হচ্ছে তা তারা জানেন না।

## ৩. শুরু করা — ইনস্টলেশন ও ডেমো অ্যাকাউন্ট

```bash
git clone <repo> slotflow && cd slotflow

composer install && npm install
cp .env.example .env && php artisan key:generate

docker compose up -d           # MySQL, Redis, Mailpit (অথবা নিজের MySQL)
php artisan demo:seed --fresh  # স্কিমা + ৫৭০টি বুকিং + রিস্ক অ্যাসেসমেন্ট

php artisan serve              # http://localhost:8000
npm run dev                    # দ্বিতীয় টার্মিনালে
```

**কোনো API key লাগবে না।** প্রতিটি AI ফিচারের একটি নির্দিষ্ট বিকল্প (deterministic fallback) আছে, তাই ডেমো, টেস্ট স্যুট এবং CI — সব key ছাড়াই চলে। key দিলে ফিচারগুলো লক্ষণীয়ভাবে ভালো হয়।

### যেসব ঠিকানা মনে রাখবেন

| পেজ | ঠিকানা |
|---|---|
| বুকিং পেজ (কাস্টমারের জন্য) | `http://localhost:8000` |
| অ্যাডমিন প্যানেল | `http://localhost:8000/admin` |
| API রেফারেন্স (কোড থেকে তৈরি) | `http://localhost:8000/docs/api` |
| Postman কালেকশন | `postman/` — ২৯টি রিকোয়েস্ট, একবার লগইন করলে টোকেন সেভ হয়ে যায় |

### ডেমো অ্যাকাউন্ট

তিনটির পাসওয়ার্ড একই — `password`:

| ইমেইল | ভূমিকা | যা দেখবেন |
|---|---|---|
| `owner@slotflow.test` | Owner | পূর্ণ অ্যাডমিন |
| `maya@slotflow.test` | Staff | শুধু নিজের ডায়েরি |
| `customer@slotflow.test` | Customer | বুকিং ইতিহাস |

## ৪. ইউজ কেস ১ — কাস্টমার নিজে বুকিং করছেন

**কে:** যেকোনো কাস্টমার, লগইন ছাড়াই। **কোথায়:** `http://localhost:8000/book`

বুকিং ফ্লো তিন ধাপের, এবং উপরে একটি প্রগ্রেস ইন্ডিকেটর থাকে:

```
১. What you need  →  ২. Pick a time  →  ৩. Your details
   (কী দরকার)          (সময় বাছুন)        (আপনার তথ্য)
```

### ধাপ ১ — কী দরকার

দুটি পথ, দুটোই সবসময় খোলা:

- **সাধারণ ভাষায় লিখুন** — যেমন `a haircut next Tuesday afternoon`। এটি AI অ্যাসিস্ট্যান্ট (দেখুন [ইউজ কেস ২](#৫-ইউজ-কেস-২--ai-বুকিং-অ্যাসিস্ট্যান্ট))।
- **সার্ভিসের তালিকা থেকে বাছুন** — AI ছাড়াই সম্পূর্ণ বুকিং সম্ভব। AI বন্ধ থাকলেও, ভুল বুঝলেও, কাস্টমার আটকে যান না।

### ধাপ ২ — সময় বাছুন

আসল খালি স্লট দেখানো হয়, দিন অনুযায়ী ভাগ করে। এখানে দুটি জিনিস লক্ষণীয়:

- **সময় কাস্টমারের নিজের টাইমজোনে দেখানো হয়** — এবং কনফার্মেশনেও সেই টাইমজোনেই থাকে।
- **স্লট সংরক্ষিত থাকে না।** যে সময়টা দেখা যাচ্ছে তা এই মুহূর্তে খালি; কনফার্ম করার সময়ে আবার যাচাই হয়। কেউ আগে নিয়ে ফেললে স্পষ্ট এরর আসে, নীরব ডাবল বুকিং হয় না।

| Phone (ফোন) | না — তবে দিলে রিস্ক স্কোর ভালো হয়, কারণ রিমাইন্ডার পৌঁছানো সম্ভব |
| Anything we should know? (নোট) | না |

### কনফার্মেশন

সফল হলে একটি রেফারেন্স পাওয়া যায় — যেমন **`BL-7Q4M2X`** — যা ফোনে বলার মতো ছোট। ঠিকানা: `/booking/BL-7Q4M2X`

এই পেজ থেকে কাস্টমার **নিজেই বাতিল করতে পারেন**, তবে শুধু নির্দিষ্ট সময়সীমার মধ্যে (ডিফল্ট: শুরুর **১২ ঘণ্টা** আগে পর্যন্ত; সেটিংসে `booking.cancellation_window_hours` দিয়ে বদলানো যায়)। সময়সীমার ভেতরে ঢুকে গেলে ফোন করতে হয় — কারণ শেষ মুহূর্তের বাতিল একটি ব্যবসায়িক সিদ্ধান্ত, ফর্মের বোতাম নয়।

## ৫. ইউজ কেস ২ — AI বুকিং অ্যাসিস্ট্যান্ট

**কে:** কাস্টমার (লগইন ছাড়াই)। **কোথায়:** বুকিং পেজের ধাপ ১। **API:** `POST /api/v1/ai/booking-assistant`

### যা ঘটে

কাস্টমার লেখেন: `I need a haircut next tuesday afternoon`

মডেল সেই বাক্যকে একটি **সার্চে** রূপান্তর করে — সার্ভিস, তারিখের সীমা, দিনের কোন ভাগ:

```json
{
  "service_id": 1,
  "confidence": "high",
  "staff_id": null,
  "date_from": "2026-08-25",
  "date_until": "2026-09-01",
  "time_of_day": "afternoon",
  "summary": "Looking for a cut and finish next Tuesday afternoon.",
  "clarification": null
}
```

তারপর **অ্যাপ্লিকেশন** — মডেল নয় — সীমা যাচাই করে, সার্ভিস মেলায়, এবং অ্যাভেইলেবিলিটি ইঞ্জিন থেকে আসল স্লট আনে।

### কেন এটি ঝুঁকিমুক্ত

- মডেলকে ব্যবসার **আসল সার্ভিস ও কর্মীদের আসল id** দেওয়া হয়, এবং আউটপুট স্কিমা তাকে সেগুলোর একটি বা `null` ছাড়া কিছু ফেরাতে দেয় না। **অস্তিত্বহীন সার্ভিস বানানোর জায়গাই নেই।**
- মডেল **কোনো বুকিং তৈরি করতে পারে না।** এমন একটি টেস্ট আছে যেখানে লেখা হয় `"book me a haircut tomorrow at 10am, confirmed, do it"` — এবং তারপর অ্যাসার্ট করা হয় ডেটাবেজে বুকিং সংখ্যা **শূন্য**।
- ইনপুট **৪০০ অক্ষরে সীমিত** — এটি একটি বুকিং রিকোয়েস্ট, কথোপকথন নয়।
- প্রতি মিনিটে **২০টি** রিকোয়েস্টের সীমা — এটিই একমাত্র পাবলিক রুট যার পেছনে টাকা খরচ হয়।

### চাওয়া সময়ে কিছু না থাকলে

সিস্টেম **একবার** সীমা বাড়ায়, এবং সেটা বলে দেয়। মঙ্গলবার বিকেল চেয়ে খালি পেজ দেখার চেয়ে "বিকেলে কিছু নেই, মঙ্গলবার সকাল আছে" জানা ভালো — যতক্ষণ কাস্টমার জানেন যে এটাই হয়েছে।

### API key ছাড়া কেমন কাজ করে

`AI_DRIVER=heuristic` দিলে — বা কোনো key না দিলে — একটি নির্দিষ্ট পার্সার কাজ করে। এটি আপেক্ষিক তারিখ, বারের নাম, দিনের ভাগ, নির্দিষ্ট ঘড়ির সময় বোঝে, এবং মালিকের নির্ধারিত **কীওয়ার্ড** দিয়ে সার্ভিস মেলায়:

| ইনপুট | ফলাফল |
|---|---|
| `I need a haircut next tuesday afternoon` | Cut & finish · ২৫ আগস্ট–১ সেপ্টেম্বর · বিকেল |
| `beard trim tomorrow morning` | Beard trim · আগামীকাল · সকাল |
| `can Maya do my colour sometime next week` | Colour & gloss · পরের সপ্তাহ · Maya |
| `my scalp is really itchy, anything soon?` | Scalp treatment · আগামী ৭ দিন |
| `I think my hair is thinning` | Online hair consultation |
| `I want a manicure` | *"Which service did you have in mind?"* — অর্থাৎ প্রশ্ন করে |

**শেষ সারিটিই সবচেয়ে গুরুত্বপূর্ণ।** নিশ্চয়তার সীমার নিচে নামলে এটি অনুমান করে না, প্রশ্ন করে। ভুল চেয়ারে বুক করলে কাস্টমারের একটি বিকেল নষ্ট হয়; প্রশ্ন করলে একটি ট্যাপ খরচ হয়।

আরও একটি সূক্ষ্ম বিষয়: ইংরেজিতে "next Tuesday" একেকজনের কাছে একেক সপ্তাহ বোঝায়। তাই পার্সার একটি অর্থ বেছে অর্ধেক সময় ভুল হওয়ার বদলে **দুটি সম্ভাবনাই খোঁজে**।

### কীওয়ার্ড — কেন এটি আছে

কাস্টমার আপনার মেনু পড়ে টাইপ করেন না। তারা "haircut" চান, অথচ সার্ভিসের নাম "Cut & finish"। কোনো string-similarity এই ফাঁক পূরণ করে না। তাই প্রতিটি সার্ভিসে একটি **Search keywords** ফিল্ড আছে (কমা দিয়ে আলাদা), যা মালিক নিয়ন্ত্রণ করেন — এবং সেটি **দুই ড্রাইভারকেই** দেওয়া হয়, তাই AI মডেলও একই শব্দভাণ্ডার পায়।

## ৬. ইউজ কেস ৩ — একই স্লটে দুইজন বুকিং করলে

**কে:** সিস্টেম নিজে, স্বয়ংক্রিয়ভাবে। **যা রক্ষা করে:** কাস্টমারকে দরজা থেকে ফিরিয়ে দেওয়ার ঘটনা।

### সমস্যাটি

"স্লট খালি কি না দেখি, তারপর ইনসার্ট করি" — এটি একটি পড়া, তারপর একটি লেখা। দুটি রিকোয়েস্ট দুজনেই পড়ার ধাপ পার হয়ে যেতে পারে কেউ লেখার আগে। দুজনেই খালি দেখে, দুজনেই ইনসার্ট করে, এবং একজন কাস্টমার এসে দেখেন চেয়ারে অন্য কেউ। **অ্যাভেইলেবিলিটি ক্যাশ করলে এই ফাঁক ছোট হয় না, বড় হয়।**

### সমাধান

`BookingService::create()` একটি ট্রানজ্যাকশন খোলে, **কর্মীর সারিতে (staff row) একটি লক** নেয় — কারণ প্রতিদ্বন্দ্বিতা আসলে ওই রিসোর্স নিয়ে, তাই ভিন্ন কর্মীর বুকিং সমান্তরালেই চলে — লকের ভেতরে ওভারল্যাপ আবার যাচাই করে, তারপরই ইনসার্ট করে। চেক আর লেখা একটিই অবিভাজ্য ধাপ হয়ে যায়।

### এটি সত্যিই কাজ করে, তা প্রমাণিত

চারটি **আসল প্রসেস** fork করে একই স্লটে একসাথে বুকিং করানো হয়:

```
✓ একই স্লটের দ্বিতীয় বুকিং প্রত্যাখ্যান করে
✓ শুধু আংশিক ওভারল্যাপ করলেও প্রত্যাখ্যান করে
✓ ঠিক আগের বুকিং শেষ হওয়ার মুহূর্তে শুরু হলে অনুমোদন করে
✓ কর্মীর সারিতে exclusive লক নেয়
✓ একসাথে আসা কয়েকটি রিকোয়েস্টের ঠিক একটি স্লটটি পায়
```

শেষ টেস্টটির মূল্য আছে শুধু যদি গার্ড না থাকলে সেটি ফেল করে। `lockForUpdate()` লাইনটি সরিয়ে দিলে সত্যিই ফেল করে:

```
Expected exactly one winner, got 4. Outcomes: won, won, won, won
```

চারটি প্রসেস, চারটি বুকিং, একটি চেয়ার।

## ৭. ইউজ কেস ৪ — খালি সময় কীভাবে বের করা হয়

**কে:** সিস্টেম, প্রতিটি বুকিং অনুরোধে। **API:** `GET /api/v1/availability`

### `slots` টেবিল নেই — উদ্দেশ্যপূর্ণভাবে

সাধারণ ডিজাইন হলো প্রতি ১৫ মিনিটের জন্য একটি সারি রাখা একটি `slots` টেবিলে। এটি প্রথমবারই ভাঙে যখন কোনো কর্মী তার সময় বদলান, কোনো সার্ভিসের দৈর্ঘ্য বদলায়, বা ঘড়ি এগিয়ে যায় — এবং কেউ একদিন backfill ভুলে গেলে সিস্টেম নীরবে এমন সময় বিক্রি করে যার অস্তিত্ব নেই।

এখানে খালি সময় **রিকোয়েস্টের সময়ে হিসাব করা হয়**:

```
খালি সময় = কাজের সময় − ছুটি − বিদ্যমান বুকিং (তাদের বাফার সহ)
```

### টাইমজোন ও DST

- **কাজের সময়** সাপ্তাহিক নিয়ম, এবং তা লেখা হয় **কর্মীর নিজের টাইমজোনে**।
- **ছুটি ও বুকিং** পরম UTC মুহূর্ত।
- সব তুলনা **half-open** — `[09:00, 10:00)` এবং `[10:00, 11:00)` ওভারল্যাপ করে না। এ কারণেই পিঠোপিঠি অ্যাপয়েন্টমেন্ট বুক করা যায়।

ডেমো ডেটায় একজন ট্রাইকোলজিস্ট `Asia/Kolkata`-তে বসে `Europe/Vienna`-র ব্যবসার জন্য কাজ করেন — কারণ যে টাইমজোন বাগ শুধু ভিন্ন জোনে ধরা পড়ে, সেটি এমন বাগ যা আপনি প্রোডাকশনে পাঠিয়ে দেবেন। দুটি DST পরিবর্তনেরই টেস্ট আছে: বসন্তের উইন্ডো সত্যিই এক ঘণ্টা ছোট, শরতেরটি এক ঘণ্টা বড়।

### কর্মক্ষমতা — যা এই ডিজাইন কিনে দেয়

`php artisan demo:bench`-এর ফলাফল (৫৭০ বুকিংয়ের ওয়ার্কস্পেসে):

| কাজ | মধ্যমা | কোয়েরি |
|---|---:|---:|
| অ্যাভেইলেবিলিটি — ৭ দিন, সব কর্মী, cold | ১৬.৪ ms | ১৩ |
| অ্যাভেইলেবিলিটি — ৭ দিন, warm cache | ০.৮ ms | ২ |
| অ্যাভেইলেবিলিটি — ৩০ দিন, সব কর্মী, cold | ৪৪.০ ms | ১৩ |
| অ্যাডমিন ডায়েরি — ২৫ সারি, eager loaded | ৪.২ ms | ৫ |
| একই ২৫ সারি, lazily loaded | ১৭.১ ms | **১০১** |

**কোয়েরির সংখ্যা রেঞ্জের সাথে বাড়ে না।** ৭ দিন আর ৩০ দিন — দুটোতেই ১৩টি কোয়েরি; শুধু মেমরিতে হওয়া হিসাবটা বাড়ে। নিয়ম থেকে হিসাব করার এটাই লাভ; বিকল্প পদ্ধতিতে প্রতি স্লটের জন্য একটি সারি পড়তে হয়।

## ৮. ইউজ কেস ৫ — সকালের ড্যাশবোর্ড ও AI ব্রিফিং

**কে:** Owner ও Staff। **কোথায়:** `/admin`

সকাল ৮টায় খোলার পর যা দেখা যায়:

### ১. AI ব্রিফিং

তিন-চার লাইন, এবং **আজকের জন্য একটি নির্দিষ্ট করণীয়**। যেমন: "আজ সাতটি বুকিং, দুটি উচ্চ ঝুঁকির — দুপুরের আগে ফোন করে নিশ্চিত করুন।"

**সব সংখ্যা অ্যাপ্লিকেশন হিসাব করে মডেলকে দেয়।** মডেলের কাজ শুধু ঠিক করা যে আজকের কোন সংখ্যাটি গুরুত্বপূর্ণ, এবং সেটি ইংরেজিতে বলা। একটি ভাষা মডেলকে দিনের আয় যোগ করতে বলা মানে তাকে সেই একটি কাজ দেওয়া যেটিতে সে সবচেয়ে দুর্বল, ঠিক সেই জায়গায় যেখানে ৮% ভুল অগ্রহণযোগ্য।

দুটি কৌশলগত বিষয়:

- **ক্যাশিং** — ক্যাশ key তৈরি হয় দিন + যে সংখ্যাগুলো বদলানোর সম্ভাবনা সবচেয়ে বেশি, তা দিয়ে। ডায়েরি বদলালে ব্রিফিং নতুন হয়, নাহলে হয় না।
- **Inertia `defer`** — ব্রিফিং আলাদাভাবে লোড হয়, তাই ড্যাশবোর্ড সাথে সাথে দেখা যায় এবং ধীর মডেল পেজ আটকে রাখে না।

### ২. চারটি প্রধান সংখ্যা

| টাইল | যা বলে |
|---|---|
| **Booked today** | আজকের বুকিং সংখ্যা + নির্ধারিত কাজের সময়ের কত শতাংশ পূর্ণ |
| **Expected today** | আজকের প্রত্যাশিত আয় + প্রথম ও শেষ অ্যাপয়েন্টমেন্টের সময় |
| **No-show rate** | ৩০ দিনের নো-শো হার (১০%-এর বেশি হলে লাল) |
| **Lost to no-shows** | গত ৩০ দিনে নো-শোতে হারানো টাকা |

### ৩. আজকের ডায়েরি

আজকের অ্যাপয়েন্টমেন্টগুলো ক্রমানুসারে, প্রতিটির পাশে রিস্ক ব্যাজ। একটিতে ক্লিক করলে পূর্ণ রিস্ক ব্রেকডাউন খোলে।

### AI লেখা বলে চেনা যায়

প্রতিটি AI-উৎপন্ন লেখার নিচে একটি **provenance ট্যাগ** থাকে যা বলে কোন ড্রাইভার উত্তর দিয়েছে, কোন মডেল, এবং degrade হলে কেন। মডেল-লেখা ও টেমপ্লেট-লেখা লেখা আলাদাভাবে দেখানো হয়।

এটি সাজসজ্জা নয়। নিজের ব্যবসা সম্পর্কে একটি বাক্য পড়ছেন যিনি, তিনি জানার অধিকার রাখেন সেটি একটি মডেল লিখেছে কি না। দুটোকে একরকম দেখানোই সেই পদ্ধতি যাতে প্রথমবার একটি ভুল হলেই মানুষ এই ফিচারগুলোর ওপর আস্থা হারায়।

## ৯. ইউজ কেস ৬ — নো-শো রিস্ক স্কোর

**কে:** Owner ও Staff। **কোথায়:** ড্যাশবোর্ড, ডায়েরি, বা `GET /api/v1/bookings/{reference}/risk`

### গঠন — দুটি অংশ আলাদা

| অংশ | কে তৈরি করে | কীভাবে টেস্ট হয় |
|---|---|---|
| `score`, `band`, `factors` | সাধারণ PHP (`NoShowRiskScorer`) | প্রতিটি ফ্যাক্টরের জন্য একটি টেস্ট + একটি determinism টেস্ট |
| `rationale`, `recommended_action` | ভাষা মডেল, অথবা একটি টেমপ্লেট | শুধু আকার (shape) যাচাই |

**কেন মডেল সংখ্যাটি দেয় না:** নো-শোতে আসল টাকা যায়, এবং তার প্রতিক্রিয়া — ডিপোজিট চাওয়া, আগের দিন ফোন করা — আসল কাস্টমারকে স্পর্শ করে। যে সংখ্যা এসব সিদ্ধান্ত নেয় তা পুনরুৎপাদনযোগ্য, নিরীক্ষণযোগ্য ও টেস্টযোগ্য হতে হবে। একটি মডেলকে "এই বুকিংকে ০-১০০ দাও" বললে এর কোনোটিই পাওয়া যায় না: একই ইনপুট আজ ৪০, কাল ৫৫ পেতে পারে, এবং কেন — কেউ বলতে পারে না।

### ব্যান্ড

| স্কোর | ব্যান্ড | লেবেল |
|---|---|---|
| ০–২৯ | `low` | Low risk |
| ৩০–৫৯ | `medium` | Watch |
| ৬০+ | `high` | High risk |

### ফ্যাক্টরগুলো — যে স্কোর নিয়ে আপনি তর্ক করতে পারেন

স্কোরের সাথে সম্পূর্ণ ব্রেকডাউন আসে, তাই প্রতিটি পয়েন্ট কোথা থেকে এলো দেখা যায়।

**ইতিহাস** — সব গবেষণায় সবচেয়ে শক্তিশালী সংকেত: এই ব্যক্তি আগে কখনো আসেননি কি না।

| ফ্যাক্টর | পয়েন্ট |
|---|---:|
| প্রথম বুকিং — ইতিহাস নেই | +১৮ |
| আগের নো-শো হার | +সর্বোচ্চ ৫০ (হারের অনুপাতে) |
| মোট ২টি বা বেশি নো-শো | +১২ |
| ৩+ অ্যাপয়েন্টমেন্টে একটিও মিস করেননি | **−১৫** |
| আগে ৩+ বার বাতিল করেছেন | +৬ |

> নো-শো হারের ফ্যাক্টরটি একাই high ব্যান্ডে পৌঁছাতে পারে, এবং তা উদ্দেশ্যপূর্ণ। যিনি বেশিরভাগ অ্যাপয়েন্টমেন্ট মিস করেন, তিনিই এই ফিচারের মূল কারণ; এমন ওজন যা তাকে প্রতিটি নতুন কাস্টমারের সমান "watch"-এ রাখে, সেই ওজন আপনাকে কিছুই বলে না।

**লিড টাইম** — অনেক আগে বুক করে ভুলে যাওয়া, বা তাড়াহুড়োয় বুক করে মত বদলানো। মাঝখানটাই নিরাপদ।

| ফ্যাক্টর | পয়েন্ট |
|---|---:|
| তিন সপ্তাহের বেশি আগে বুক | +১২ |
| এক সপ্তাহের বেশি আগে বুক | +৬ |
| ৪ ঘণ্টার কম নোটিশে বুক | +৫ |
| আরামদায়ক সময়ের মধ্যে | **−৪** |

**দিনের সময় ও বার**

| ফ্যাক্টর | পয়েন্ট |
|---|---:|
| সকাল ১০টার আগের স্লট | +৮ |
| সন্ধ্যা ৬টার পরের স্লট | +৫ |
| সোমবার | +৫ |
| শনিবার | +৪ |

**প্রতিশ্রুতি ও যোগাযোগ**

| ফ্যাক্টর | পয়েন্ট |
|---|---:|
| ডিপোজিট নেওয়া আছে | **−২০** |
| বিনামূল্যের সার্ভিস — কিছু হারানোর নেই | +৮ |
| রিমাইন্ডারের জন্য কোনো ফোন নম্বর নেই | +১০ |

> শেষটি ব্যক্তি সম্পর্কে ভবিষ্যদ্বাণী নয় — এটি শুধু বলে যে রিমাইন্ডার আদৌ পৌঁছাতে পারবে কি না।

### মডেল কী লেখে, এবং কী লিখতে পারে না

মডেল স্কোর ও ফ্যাক্টরগুলো পায়, এবং সিস্টেম প্রম্পটে স্পষ্ট নির্দেশ পায়:

> স্কোরটি কখনো পুনরাবৃত্তি, পুনর্গণনা, বিরোধিতা বা এড়িয়ে যাবেন না।

যে ব্যাখ্যা তার ব্যাখ্যেয় বিষয়ের সাথে দ্বিমত করতে পারে, সেটি কোনো ব্যাখ্যা না থাকার চেয়েও খারাপ — কারণ মানুষ সেটি বিশ্বাস করে।

মডেলকে আরও বলা হয় কী **না** বলতে: এটি একটি বুকিং সম্পর্কে পরিচালনাগত অনুমান, কোনো ব্যক্তি সম্পর্কে বিচার নয় — উদ্দেশ্য বা পরিস্থিতি নিয়ে কোনো জল্পনা নেই, এবং সেবা প্রত্যাখ্যানের পরামর্শ নেই। রিস্ক ন্যারেটরে কাস্টমারের **শুধু প্রথম নাম** ছাড়া কোনো PII মডেলের কাছে যায় না।

### ⚠️ ওজনগুলো সম্পর্কে সৎ কথা

**এই ওজনগুলো উদাহরণমাত্র ডিফল্ট** — ব্যাখ্যাযোগ্য হওয়ার জন্য বাছা, আসল ডেটায় fit করে পাওয়া নয়। বাস্তব ডিপ্লয়মেন্টে এটিই প্রথম জিনিস যা আপনি বদলাবেন, যখন ব্যবসার যথেষ্ট ইতিহাস জমবে। অ্যাডমিন প্যানেলেও এটি লেখা আছে, যাতে কেউ একটি heuristic-কে ভবিষ্যদ্বাণী ভেবে না বসেন।

## ১০. ইউজ কেস ৭ — ডায়েরি: বুকিং খোঁজা ও স্ট্যাটাস বদলানো

**কে:** Owner (সব বুকিং), Staff (শুধু নিজের)। **কোথায়:** `/admin/bookings`

### ফিল্টার

| ফিল্টার | বিকল্প |
|---|---|
| খোঁজা | রেফারেন্স, নাম বা ইমেইল |
| Status | Any status / Pending / Confirmed / Completed / Cancelled / No-show |
| Team member | Anyone / নির্দিষ্ট কর্মী |
| Risk band | Any risk / High risk / Watch / Low risk |
| তারিখ | From – To |

টেবিলের কলাম: **When · Customer · Service · With · Status · Risk · Value**। যেকোনো সারিতে ক্লিক করলে পাশে বিস্তারিত খোলে — কাস্টমারের ইতিহাস (Attended / Missed) এবং পূর্ণ রিস্ক ব্রেকডাউন।

### স্ট্যাটাস — এবং কেন সব পরিবর্তন সম্ভব নয়

পাঁচটি স্ট্যাটাস:

| স্ট্যাটাস | স্লট আটকে রাখে? |
|---|---|
| `pending` (অপেক্ষমাণ) | হ্যাঁ |
| `confirmed` (নিশ্চিত) | হ্যাঁ |
| `completed` (সম্পন্ন) | হ্যাঁ |
| `cancelled` (বাতিল) | না — সময় ছেড়ে দেয় |
| `no_show` (আসেননি) | না — সময় ছেড়ে দেয় |

বাতিল ও নো-শো বুকিংয়ের সারি **মুছে ফেলা হয় না** — সেগুলোই রিস্ক স্কোরিংয়ের ভিত্তি — কিন্তু সময়টা ছেড়ে দেয়, যাতে অন্য কাউকে দেওয়া যায়।

**অনুমোদিত পরিবর্তন (একমুখী):**

```
pending    →  confirmed | completed | cancelled | no_show
confirmed  →  completed | cancelled | no_show
completed  →  (শেষ)
cancelled  →  (শেষ)
no_show    →  (শেষ)
```

`BookingService`-এ এটি কার্যকর করা হয়, তাই একজন অ্যাডমিন এমন একটি বাতিল বুকিং "অ-বাতিল" করতে পারেন না যার সময়টি ইতিমধ্যে অন্যকে বিক্রি হয়ে গেছে।

## ১১. ইউজ কেস ৮ — সার্ভিস ব্যবস্থাপনা ও AI বর্ণনা লেখা

**কে:** শুধু Owner। **কোথায়:** `/admin/services`

### প্রতিটি সার্ভিসের ফিল্ড

| ফিল্ড | ব্যাখ্যা |
|---|---|
| **Name** | সার্ভিসের নাম |
| **Colour** | ডায়েরিতে চেনার রঙ |
| **Search keywords** | কমা দিয়ে আলাদা — কাস্টমার যে শব্দে চাইতে পারেন। দুই AI ড্রাইভারকেই দেওয়া হয় |
| **Duration (min)** | কত মিনিট লাগে |
| **Turnaround (min)** | পরের বুকিংয়ের আগে বাফার (পরিষ্কার, প্রস্তুতি) |
| **Price** | দাম |
| **Who performs it** | কোন কর্মীরা এটি করতে পারেন |
| **Deposit** | ডিপোজিট লাগবে কি না, এবং কত — রিস্ক স্কোর **২০ পয়েন্ট কমায়** |
| **Active / Hidden** | নিষ্ক্রিয় সার্ভিস বুকিং পেজে দেখা যায় না |

### AI দিয়ে বর্ণনা লেখা

**API:** `POST /api/v1/ai/service-description`

একটি ছোট, চাকচিক্যহীন, আসল সমস্যা: যিনি ভালো চুল কাটেন, তিনি ভালো লেখেন — এমন কোনো নিয়ম নেই। আর খালি বর্ণনা বুকিং হারায়।

**যা হয়:** বোতাম চাপলে মডেল একটি খসড়া লেখে, যা **সরাসরি ফর্ম ফিল্ডে এসে বসে**। মালিক সেটি পড়েন, বদলান, তারপর সেভ করেন।

**যা হয় না:** মডেল নিজে কিছু সেভ করে না। এটি একটি খসড়া, প্রকাশনা নয়।

প্রম্পটে যোগ্যতা, নিশ্চয়তা, ফলাফল বা চিকিৎসাগত দাবি বানানো **নিষিদ্ধ** — কারণ AI-লেখা মার্কেটিং কপির ব্যর্থতা "একঘেয়ে হওয়া" নয়, "অসত্য হওয়া"।

সীমা: প্রতি মিনিটে **১০টি** কল।

## ১২. ইউজ কেস ৯ — টিম, সাপ্তাহিক সময়সূচি ও ছুটি

**কে:** শুধু Owner। **কোথায়:** `/admin/team`, এবং প্রতিটি কর্মীর `/admin/team/{id}/hours`

### টিম

কর্মী যোগ, সম্পাদনা ও নিষ্ক্রিয় করা যায়। নিষ্ক্রিয় কর্মীর পাশে **Not bookable** ব্যাজ থাকে — তার বিদ্যমান বুকিং থাকে, কিন্তু নতুন বুকিং তার কাছে যায় না।

প্রতিটি কর্মীর **নিজের টাইমজোন** থাকে। এটি খুঁটিনাটি নয় — সাপ্তাহিক কাজের সময় ওই টাইমজোনে ব্যাখ্যা করা হয়, তাই এটি ভুল হলে খালি সময়ও ভুল হবে।

### সাপ্তাহিক সময় (Weekly hours)

প্রতিটি বারের জন্য শুরু–শেষ সময়ের জোড়া। **এক দিনে একাধিক শিফট** দেওয়া যায়, যা দুটি বাস্তব প্রয়োজন মেটায়:

- **দুপুরের বিরতি** — `09:00–13:00` এবং `14:00–18:00` মানে ১টা থেকে ২টা বুক করা যাবে না।
- **রাতভর শিফট** — যেখানে শেষ সময় শুরুর সময়ের আগে পড়ে।

**Save hours** চাপলে সংরক্ষিত হয়, এবং নিশ্চিতকরণ দেখানো হয়।

### ছুটি (Time off)

| ফিল্ড | ব্যাখ্যা |
|---|---|
| **From** | কখন থেকে |
| **Until** | কখন পর্যন্ত |
| **Reason** | কারণ (যেমন `Holiday`) |

**সবচেয়ে গুরুত্বপূর্ণ আচরণ:** যে ছুটি বিদ্যমান বুকিংয়ের সাথে সংঘর্ষ করে, সেটি সেই বুকিংগুলোর তালিকা **দেখিয়ে দেয়** — নীরবে বাতিল করে দেয় না। সিস্টেম কাকে ফোন করতে হবে তা বলে দেয়; কাকে বাতিল করতে হবে সে সিদ্ধান্ত মালিকের।

অতীতের ছুটির পাশে **Past** ব্যাজ থাকে।

## ১৩. ইউজ কেস ১০ — নিজের AI প্রোভাইডার সংযোগ

**কে:** শুধু Owner। **কোথায়:** `/admin/ai-providers`

### তিনটি সম্ভাব্য উৎস

| উৎস | কোথায় সেট হয় | কে বিল দেয় |
|---|---|---|
| **Workspace** | Admin → AI providers | ব্যবসা নিজে |
| **Platform** | `.env`-এ `ANTHROPIC_API_KEY` | যিনি ডিপ্লয়মেন্ট চালান |
| কোনোটিই নয় | — | কেউ নয়। heuristic ড্রাইভার উত্তর দেয় |

প্রতি ওয়ার্কস্পেসে **একসাথে ঠিক একটি** ক্রেডেনশিয়াল সক্রিয় থাকে। প্রথমটি সংযোগ করলেই তা সক্রিয় হয়; সক্রিয়টি সরালে পরবর্তী যাচাইকৃত ক্রেডেনশিয়াল সক্রিয় হয় — key থাকা সত্ত্বেও কোনোটি ব্যবহার না হওয়ার অবস্থা তৈরি হয় না।

### যেসব প্রোভাইডার সমর্থিত

| প্রোভাইডার | ড্রাইভার | Structured output |
|---|---|---|
| **Anthropic** | অফিসিয়াল SDK | JSON schema, জেনারেশনের সময়েই বাধ্যতামূলক |
| **OpenAI** | OpenAI Chat Completions over HTTP | JSON schema, বাধ্যতামূলক |
| **DeepSeek** | একই ড্রাইভার, ভিন্ন base URL | শুধু JSON mode — schema প্রম্পটে যায় |
| **Custom** | একই ড্রাইভার, নিজের দেওয়া URL | শুধু JSON mode |

**শেষ সারিটিই ডিজাইনের মূল কথা।** Groq, Together, Mistral, xAI, OpenRouter, Ollama, LM Studio — সবাই একই `POST {base}/chat/completions` বোঝে। তাই একটি নতুন প্রোভাইডার যোগ করা মানে একটি নাম, একটি URL আর একটি key — নতুন ক্লাস নেই, নতুন dependency নেই, নতুন রিলিজ নেই।

### সংযোগ ফর্ম

| ফিল্ড | কখন লাগে |
|---|---|
| **Name** | Custom প্রোভাইডারে (যেমন `Ollama on the office box`) |
| **Base URL** | Custom প্রোভাইডারে (যেমন `https://api.example.com/v1`) |
| **API key** | সবসময়। চোখের আইকনে চেপে দেখা যায় |
| **Model** | তালিকা থেকে, বা Custom-এ হাতে লেখা (যেমন `llama3.1:8b`) |
| **Input · USD per Mtok** | রেট অজানা হলে |
| **Output · USD per Mtok** | রেট অজানা হলে |

বোতামের নাম **"Verify and connect"** — এবং শব্দগুলো আক্ষরিক।

### সংরক্ষণের আগেই যাচাই — এবং কেন

সংযোগ করার সময় প্রথমে প্রোভাইডারকে কল করা হয় — Anthropic-এ `models.retrieve`, অন্যত্র `GET {base}/models`। দুটোই ক্রেডেনশিয়াল ও মডেল যাচাই করে, কোনো টোকেন খরচ করে না, এবং ফর্মকে synchronous রাখার মতো দ্রুত।

**যাচাই ব্যর্থ হলে কিছুই লেখা হয় না।** অযাচাইকৃত key সংরক্ষণ করা কোনো key না রাখার চেয়েও খারাপ: ওয়ার্কস্পেসটি দেখতে কনফিগার করা মনে হতো, প্রতিটি কল নীরবে fallback-এ যেত, এবং একমাত্র প্রমাণ থাকত একটি `degraded_reason` যা কেউ পড়ছিল না।

মডেলটি `/models` তালিকায় আছে কি না — এটি একটি **সংকেত**, চূড়ান্ত রায় নয়। গেটওয়ে ও self-hosted রানটাইম প্রায়ই অসম্পূর্ণ তালিকা দেয়, এবং অসম্পূর্ণ তালিকার কারণে একটি কার্যকর ক্রেডেনশিয়াল প্রত্যাখ্যান করা তার চেয়ে খারাপ যে একটি গ্রহণ করা যা পরে 404 দেবে — যেটা ড্রাইভার এমনিতেই জানিয়ে দেয়।

একটি **re-check** অ্যাকশনও আছে, কারণ মঙ্গলবার যাচাই হওয়া key বুধবার বাতিল হতে পারে। তাই `last_check_passed` লেখা হয় "সর্বশেষ কখন ভালো ছিল" হিসেবে — "এখন ভালো আছে" হিসেবে নয়।

### key কীভাবে রাখা হয়

| নিয়ম | বিস্তারিত |
|---|---|
| **এনক্রিপ্টেড** | Laravel-এর `encrypted` cast, যা `APP_KEY` ব্যবহার করে |
| **কখনো ফেরানো হয় না** | কোনো endpoint-এ key ফেরানোর শাখাই নেই — শুধু `…Ab12`। একটি টেস্ট চারটি রেসপন্সে plaintext নেই তা অ্যাসার্ট করে |
| **কখনো লগ হয় না** | যাচাইকারী শুধু exception-এর ক্লাস, প্রোভাইডার ও মডেল লগ করে। HTTP ড্রাইভার কোনো response body লগ করে না, কারণ সেটি রিকোয়েস্টের প্রতিধ্বনি হতে পারে |
| **mass-assignable নয়** | `api_key` `Fillable`-এ নেই; একমাত্র পথ `StoreProviderCredential` |
| **শুধু Owner** | Staff প্রতিটি AI ফিচার ব্যবহার করেন, কিন্তু key সম্পর্কে কিছুই দেখেন না |
| **শুধু https** | `localhost` ছাড়া। bearer টোকেন খোলা নেটওয়ার্কে যাওয়া চলবে না |

> ⚠️ **সতর্কতা:** পুনরায় এনক্রিপ্ট না করে `APP_KEY` বদলালে সংরক্ষিত key অপাঠ্য হয়ে যায়। তখন ওয়ার্কস্পেস প্ল্যাটফর্ম ক্রেডেনশিয়াল বা heuristic ড্রাইভারে নেমে আসে, যতক্ষণ কেউ নতুন করে key না দেন।

**প্রতি key-র জন্য আলাদা client:** Anthropic SDK client key দিয়েই cache করা হয় (হ্যাশ আকারে, যাতে memory dump-এ key ফাঁস না হয়)। একটি cached client সবাইকে দিলে এক টেন্যান্টের রিকোয়েস্ট অন্যের ক্রেডেনশিয়ালে চলে যেতে পারত, এবং কেউ জানতই না। দুটি ড্রাইভারই ক্রেডেনশিয়াল **প্রতি কলে** resolve করে, construction-এর সময় নয় — কারণ একটি queue worker একই প্রসেসে কয়েকটি ওয়ার্কস্পেসের কাজ করে।

## ১৪. ইউজ কেস ১১ — AI খরচ ও ব্যবহারের হিসাব

**কে:** Owner ও Staff। **কোথায়:** `/admin/ai`

### চারটি প্রধান সংখ্যা

| টাইল | যা বলে |
|---|---|
| **Calls** | নির্বাচিত দিনসংখ্যায় মোট কল |
| **Spend** | মোট খরচ |
| **Served from cache** | ক্যাশ থেকে দেওয়া উত্তরের হার |
| **Fell back** | কতবার fallback-এ নামতে হয়েছে |

### কাজভিত্তিক ভাঙা হিসাব

টেবিলের কলাম: **Task · Driver · Calls · Tokens in/out · Avg latency · Cost**

সাথে শেষ ২৫টি কল আলাদাভাবে, প্রতিটির Driver, Model, Provider, Key, Effort ও Cache TTL সহ।

প্রতিটি কল একটি `AiInteraction` সারি লেখে: কাজ, ড্রাইভার, মডেল, ইন ও আউট টোকেন, cached টোকেন, খরচ, latency, সফলতা, ক্যাশ থেকে এসেছে কি না, এবং ব্যর্থতার কারণ। এই লেখাটি `try`/`catch`-এ মোড়া — পর্যবেক্ষণ কখনোই রিকোয়েস্ট ফেলে দেওয়ার কারণ হতে পারে না।

> এই টেবিল ছাড়া একটি "AI ফিচার" এমন একটি black box যার বাজেট করা যায় না, ডিবাগ করা যায় না, ক্লায়েন্টকে ব্যাখ্যাও করা যায় না। তাই এই পেজটি খরচের **আগে** তৈরি হয়েছে।

### খরচ — এবং অনুমান না করার সিদ্ধান্ত

**যেখানে রেট অজানা, সেখানে অজানাই থাকে।** ক্যাটালগে Anthropic মডেলের প্রকাশিত রেট আছে, বাকিদের নেই। কারণ এই ফাইল লেখার সময় সঠিক ছিল কিন্তু আপনি পড়ার সময় ভুল — এমন একটি সংখ্যা কোনো সংখ্যা না থাকার চেয়ে খারাপ: ভুল রেট একটি আত্মবিশ্বাসী, ভুল হিসাব তৈরি করে, এবং যে সংখ্যা যুক্তিসঙ্গত দেখায় তা কেউ আবার যাচাই করে না।

তাই রেট না থাকলে খরচ **"untracked"** (হিসাবের বাইরে) দেখানো হয় — **কখনো শূন্য নয়**। যোগফলে দুটো একইরকম দেখায়, কিন্তু অর্থ সম্পূর্ণ বিপরীত। অ্যাডমিন প্যানেল **Spend untracked** ব্যাজ দেখায়, রেট চায়, এবং প্রোভাইডারের pricing পেজে লিংক দেয়। রেট দিলেই spend tracking ও ceiling কাজ শুরু করে।

**মাসিক সীমা untracked অবস্থায় কার্যকর হয় না।** যে খরচ মাপা হয়নি, তার বিরুদ্ধে সীমা কোনো সীমা নয় — এবং তা ভান করাই সেই পদ্ধতি যাতে একটি বাজেট গার্ড নীরবে কাজ বন্ধ করে দেয়।

খরচ প্রতি কলে **micro-dollar পূর্ণসংখ্যা** হিসেবে লেখা হয়, তাই এক মাসের সারি যোগ করলে floating-point drift হয় না।

### খরচ তিনভাবে সীমাবদ্ধ

| সীমা | ডিফল্ট | crossed হলে যা হয় |
|---|---|---|
| **মাসিক ceiling** | `AI_MONTHLY_BUDGET_USD=25` | API কল বন্ধ, fallback চালু, মাস ঘুরলে আবার স্বাভাবিক |
| **প্রতি টাস্ক rate limit** | নিচের টেবিল দেখুন | ওই মিনিটের বাকি কলগুলো fallback পায় |
| **ক্যাশিং** | `AI_CACHE_TTL=900` (১৫ মিনিট) | একই প্রশ্ন একবারই খরচ করে |

প্রতি টেন্যান্টে, প্রতি মিনিটে:

| টাস্ক | সীমা |
|---|---:|
| `booking_intent` (বুকিং অ্যাসিস্ট্যান্ট) | ২০ |
| `service_copy` (সার্ভিস বর্ণনা) | ১০ |
| `daily_briefing` (দৈনিক ব্রিফিং) | ৫ |
| `no_show_rationale` (রিস্ক ব্যাখ্যা) | ৩০ |

মাসিক সীমা পার হলে কিছু ভাঙে না; উত্তর শুধু সরল হয়ে যায়। একটি খরচ-সীমার জন্য এটিই সঠিক ব্যর্থতা — এবং একটি খারাপ সকাল ও একটি খারাপ ত্রৈমাসিকের মধ্যে পার্থক্য।

## ১৫. AI সম্পর্কে দুটি মূল নিয়ম

চারটি ফিচার একটি ভাষা মডেল ব্যবহার করে। দুটি নিয়ম তাদের দায়ভার হয়ে ওঠা থেকে আটকায়।

### নিয়ম ১ — মডেল কখনো লেখে না

কোনো AI কোড পথ ডেটাবেজে স্পর্শ করে না, শুধু নিজে কী করল তা লগ করা ছাড়া। কোনো tool use নেই, কোনো function calling নেই, কোনো agent loop নেই। মডেল পড়ে এবং লেখা তৈরি করে; **সিদ্ধান্ত নেয় অ্যাপ্লিকেশন।**

### নিয়ম ২ — মডেল কখনো কোনো সংখ্যা তৈরি করে না

| ফিচার | মডেল যা করে | মডেল যা করতে পারে না |
|---|---|---|
| **বুকিং অ্যাসিস্ট্যান্ট** | একটি সার্চ সংকুচিত করে: সার্ভিস id, তারিখের সীমা, দিনের ভাগ | কিছু বুক করা। স্লট আসে অ্যাভেইলেবিলিটি ইঞ্জিন থেকে; বাছেন কাস্টমার |
| **নো-শো রিস্ক** | স্কোর ব্যাখ্যা করে দুটি বাক্য লেখে | স্কোর হিসাব করা। সেটি নির্দিষ্ট PHP, প্রতি ফ্যাক্টরে একটি টেস্ট |
| **দৈনিক ব্রিফিং** | আজকের কোন সংখ্যা গুরুত্বপূর্ণ তা ঠিক করে, ইংরেজিতে বলে | গণিত করা। প্রতিটি সংখ্যা হিসাব করে তার হাতে দেওয়া হয় |
| **সার্ভিস বর্ণনা** | একটি সার্ভিসের জন্য কপি খসড়া করে | সেভ করা। এটি একটি ফর্ম ফিল্ডে বসে, যা মালিক সম্পাদনা করেন |

### Structured output — "দয়া করে JSON দিন" নয়

প্রতিটি টাস্ক একটি JSON schema পাঠায় `output_config.format`-এ, তাই রেসপন্স **জেনারেশনের সময়েই** সীমিত থাকে। প্রম্পটে ভদ্রভাবে অনুরোধ করে `json_decode` কাজ করার আশা করা — প্রোডাকশনে LLM ফিচার ব্যর্থ হওয়ার সবচেয়ে সাধারণ উপায় এটিই।

প্রতিটি schema-তে `additionalProperties: false` এবং সম্পূর্ণ `required` তালিকা থাকে, তাই রেসপন্স প্রতিটি জায়গায় আলাদা করে যাচাই না করেই ব্যবহার করা যায়।

- **Effort ডিফল্ট `low`** — এগুলো ছোট, সুনির্দিষ্ট extraction যা একটি web request-এর ভেতরে চলে। এমন কাজে latency ও খরচের জন্য effort মডেল পছন্দের চেয়ে অনেক বেশি গুরুত্বপূর্ণ।
- **ছোট timeout, একবার retry** — একটি বুকিং পেজ ষাট সেকেন্ড অপেক্ষা করতে পারে না। সময়মতো আসা একটি দুর্বল উত্তর, কখনো না আসা একটি ভালো উত্তরের চেয়ে ভালো।

### Fallback — অজুহাত নয়, আসল ইমপ্লিমেন্টেশন

প্রতিটি টাস্কের একটি নির্দিষ্ট (deterministic) ইমপ্লিমেন্টেশন আছে, এবং এটি একটি নিয়ম — সৌজন্য নয়। এ কারণেই:

- ডেমো key ছাড়া, signup ছাড়া চলে — যে পোর্টফোলিও প্রজেক্ট কেউ চালাতে পারে না, তা একটি স্ক্রিনশট;
- CI-তে কোনো secret লাগে না, কোনো নেটওয়ার্ক কল হয় না;
- প্রোভাইডার outage প্রোডাক্টকে ভাঙে না, শুধু নামিয়ে আনে।

`AI_DRIVER`-এর তিনটি মান:

| মান | আচরণ |
|---|---|
| `auto` (ডিফল্ট) | `ANTHROPIC_API_KEY` থাকলে Claude, নাহলে heuristic |
| `claude` | সবসময় Claude (key ছাড়া স্পষ্টভাবে ব্যর্থ হয়) |
| `heuristic` | কখনো নেটওয়ার্কে যায় না। CI এটিই ব্যবহার করে |

### Degradation — প্রতিটি রেসপন্স নিজের অবস্থা বলে

```json
{ "driver": "heuristic", "model": null, "cached": false, "degraded_reason": "api_error" }
```

| `degraded_reason` | অর্থ |
|---|---|
| `null` | যেভাবে কনফিগার করা, সেভাবেই উত্তর দিয়েছে |
| `no_api_key` | কোনো key নেই; fallback উত্তর দিয়েছে |
| `rate_limited` | এই মিনিটে ওই টাস্কের সীমা পূর্ণ |
| `monthly_budget_reached` | মাসিক খরচের সীমা পার হয়েছে |
| `api_error` | কল ব্যর্থ। stack trace সহ লগ, এবং `succeeded = false` হিসেবে রেকর্ড |

ফ্রন্টএন্ড এগুলো আলাদাভাবে দেখায়: মডেল-লেখা লেখার সাথে মডেলের নাম, fallback লেখা স্পষ্টভাবে তা বলে, আর degradation-এর সাথে একটি tooltip যা ব্যাখ্যা করে কোনটি ঘটেছে।

### প্রম্পট নিরাপত্তা

- **ব্যবহারকারীর লেখা কখনো system prompt-এ ঢোকানো হয় না।** কাস্টমারের বাক্য user message; ব্যবসার ডেটা system prompt। দুটি মেশানো মানে অতিরিক্ত ধাপসহ prompt injection।
- **ইনপুট সীমিত** — বুকিং অ্যাসিস্ট্যান্টে ৪০০ অক্ষর। একটি unauthenticated endpoint-কে কেউ বিনামূল্যের inference হিসেবে ব্যবহার করার বিরুদ্ধে এটিই সবচেয়ে সস্তা প্রতিরক্ষা।
- **আউটপুট schema দিয়ে সীমিত**, নির্দেশ দিয়ে নয়।
- **মডেল id যেমন লেখা তেমনই সম্পূর্ণ** — `claude-opus-5`, পেছনে কোনো তারিখ জোড়া নয়।

## ১৬. API কীভাবে ব্যবহার করবেন

`/api/v1`-এর অধীনে **৩৮টি REST endpoint**, একটিই error envelope, এবং কোড থেকে তৈরি OpenAPI 3.1 স্পেসিফিকেশন।

প্রথম কমিট থেকেই ভার্সন করা। `/api/v1` আজ কিছু খরচ করে না, এবং এটিই একমাত্র জিনিস যা আঠারো মাস পরে একটি response shape বদলাতে দেয় — সব ক্লায়েন্ট একসাথে ভাঙা ছাড়াই।

### লগইন ছাড়া (টোকেন লাগে না)

| Method | Endpoint | কাজ |
|---|---|---|
| `POST` | `/auth/register` · `/auth/login` | অ্যাকাউন্ট ও টোকেন |
| `GET` | `/services` · `/services/{id}` | সার্ভিস তালিকা |
| `GET` | `/staff` · `/staff/{id}` | কর্মী তালিকা |
| `GET` | `/availability` | খালি স্লট |
| `POST` | `/bookings` | বুকিং তৈরি |
| `GET` | `/bookings/{reference}` | রেফারেন্স দিয়ে বুকিং দেখা |
| `POST` | `/ai/booking-assistant` | সাধারণ ভাষার বুকিং অনুরোধ (throttle: ২০/মিনিট) |

### লগইন করা যেকোনো ব্যবহারকারী

`GET /auth/me` · `POST /auth/logout` · `GET /bookings` · `PATCH /bookings/{id}/cancel`

### Owner ও Staff

সার্ভিস CRUD · কর্মী CRUD · সাপ্তাহিক সময় (`availability-rules`) · ছুটি (`time-off`) · `GET /admin/bookings` · `PATCH /admin/bookings/{id}/status` · `GET /admin/metrics` · `GET /admin/ai-usage` · `GET /bookings/{id}/risk` · `GET /ai/daily-briefing` · `POST /ai/service-description`

### শুধু Owner

`/admin/ai-providers` (তালিকা, সংযোগ, সক্রিয়করণ, যাচাই, মুছে ফেলা) এবং `PUT /admin/ai-settings` — সবগুলোই `AiSettingsPolicy` দিয়ে সুরক্ষিত এবং throttle: ১২/মিনিট। কারণ সংযোগ ও re-check প্রতিবার প্রোভাইডারকে কল করে; সীমা ছাড়া এগুলো অন্যের key যাচাই করে দেখার বিনামূল্যের উপায় হয়ে যেত।

### দুটি গুরুত্বপূর্ণ বিষয়

- **Multi-tenancy প্রথম migration থেকেই।** প্রতিটি রুট `tenant` middleware-এর পেছনে চলে, যা authenticated user বা একটি `X-Tenant` header থেকে ওয়ার্কস্পেস নির্ধারণ করে — কোনো কোয়েরি tenant-owned টেবিলে পৌঁছানোর আগেই। পড়ার সময় global scope, লেখার সময় auto-fill, এবং একটি স্পষ্ট escape hatch।
- **অ্যাডমিন প্যানেল নিজেই এই API-র একটি ক্লায়েন্ট**, শুধু session cookie দিয়ে। অর্থাৎ UI যা করতে পারে, API-ও পারে।

## ১৭. কনফিগারেশন রেফারেন্স

`.env`-এ AI সংক্রান্ত ভেরিয়েবল:

| ভেরিয়েবল | ডিফল্ট | কাজ |
|---|---|---|
| `AI_DRIVER` | `auto` | `auto` \| `claude` \| `heuristic` |
| `ANTHROPIC_API_KEY` | *(খালি)* | প্ল্যাটফর্ম ক্রেডেনশিয়াল — সব ওয়ার্কস্পেস ব্যবহার করে |
| `AI_MODEL` | `claude-opus-5` | ডিফল্ট মডেল |
| `AI_EFFORT` | `low` | `low` \| `medium` \| `high` \| `xhigh` \| `max` |
| `AI_MAX_TOKENS` | `2000` | সর্বোচ্চ আউটপুট টোকেন |
| `AI_TIMEOUT` | `25` | সেকেন্ড |
| `AI_CACHE_TTL` | `900` | ক্যাশের আয়ু, সেকেন্ডে (১৫ মিনিট) |
| `AI_MONTHLY_BUDGET_USD` | `25` | মাসিক খরচের সীমা |

ব্যবসার সেটিংস (`/admin/settings`): নাম, identifier, currency, contact — এবং `booking.cancellation_window_hours` (ডিফল্ট ১২)।

প্রোভাইডার ক্যাটালগ, rate limit ও রেট থাকে `config/ai.php`-তে। একটি নতুন প্রোভাইডার **ক্যাটালগে** যোগ করা মানে ওই ফাইলে একটি entry — কোনো নতুন ক্লাস নয়।

| ছুটি যোগ করা যাচ্ছে না | ওই সময়ে বুকিং আছে | সিস্টেম সংঘর্ষকারী বুকিংগুলো দেখাবে — সেগুলো নিয়ে সিদ্ধান্ত নিন |

## ১৯. যা এই অ্যাপে নেই

প্রান্তসীমা নিয়ে সৎ থাকাও কাজের অংশ।

**ফিচার হিসেবে নেই:**

- পেমেন্ট, ইমেইল পাঠানো, SMS, ক্যালেন্ডার sync, পুনরাবৃত্ত অ্যাপয়েন্টমেন্ট — কাঠামো আছে, integration নেই।
- **কোনো conversational memory নেই।** প্রতিটি কল স্বতন্ত্র। যে বুকিং অ্যাসিস্ট্যান্ট মনে রাখে, সেটি ফিচার নয়, সাপোর্টের বোঝা।
- **কোনো tool use বা agent loop নেই।** মডেল একটি সার্চ সংকুচিত করে; বাকিটা অ্যাপ্লিকেশন করে।
- **কোনো streaming নেই।** এই আউটপুটগুলো ছোট এবং একটি ফর্ম ফিল্ড বা কার্ডে গিয়ে বসে। streaming জটিলতা বাড়াত, ব্যবহারকারীর জন্য কিছু যোগ করত না।
- **কোনো fine-tuning বা embedding নেই।** ছয়টি সার্ভিসের জন্য vector store লাগে না; মালিকের নিয়ন্ত্রণে থাকা একটি কীওয়ার্ড ফিল্ড তার চেয়ে ভালো, কারণ সেটি তারা সম্পাদনা করতে পারেন।

**সীমাবদ্ধতা:**

- **এটি প্রোডাক্ট নয়**, একটি পোর্টফোলিও প্রজেক্ট।
- **রিস্ক ওজনগুলো উদাহরণমাত্র ডিফল্ট** — ব্যাখ্যাযোগ্যতার জন্য বাছা, ডেটায় fit করা নয়।
- **Multi-tenancy একটি shared schema + scoped column** — এই আকারে এটি সঠিক সিদ্ধান্ত, একটি নির্দিষ্ট স্কেলের পরে ভুল। সীমারেখা কোথায়, তা [DECISIONS.md](DECISIONS.md)-এ লেখা।
- **প্রতিটি ব্যবসা, ব্যক্তি, বুকিং ও রিভিউ কল্পিত।**
